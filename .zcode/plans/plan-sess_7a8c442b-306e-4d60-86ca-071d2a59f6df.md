## Goal

Update `spec_doc/PRINT_KIOSK_SPEC.md` so **local development requires zero Docker**: SQLite file for the DB and on-disk storage for uploads. Production stays as designed (PostgreSQL 16 + Cloudflare R2). The repo is spec-only today (no code), so this change is entirely spec edits that the build phases will implement against.

## Verified constraints (drive the schema changes)

- Prisma's SQLite connector does **not** support `Json` fields or `enum` types — the current data model uses both (`settings Json`, `inkLevels Json`, `data Json`, `JobState`, `KioskStatus`).
- Prisma cannot set `provider` from an env var — dev/prod provider switching requires two schema files.

## Edits to `spec_doc/PRINT_KIOSK_SPEC.md`

**1. Header (after line 5)** — add a local-dev principle: dev machines run no Docker (SQLite + on-disk storage via a StorageService adapter); production runs PostgreSQL 16 + R2; CI runs the suite against Postgres to catch drift.

**2. §2 Monorepo layout** — remove the `docker-compose.yml` entry; add a `.local/` entry (gitignored: `dev.db` SQLite file + `uploads/` storage dir).

**3. §3 Tech stack table**
- API row → "NestJS, Prisma, PostgreSQL 16 (prod) / SQLite (local dev)"
- File storage row → "Cloudflare R2 in prod; local dev: StorageService adapter writing to `.local/uploads` on disk (no MinIO)"

**4. §4 Data model — add a "SQLite compatibility" note block after the schema**
- `Json` fields → `String` columns storing serialized JSON, parsed/validated by zod schemas in `packages/shared` at the service boundary.
- `JobState` / `KioskStatus` enums → `String` columns typed as TS unions + zod enums in `packages/shared` (app enforces valid values).
- Two schema files: canonical `prisma/schema.prisma` (`provider = postgresql`, migrations for prod/CI) and `prisma/schema.sqlite.prisma` (`provider = sqlite`, local dev via `prisma db push` — no migration files locally).
- CI safeguard: a pipeline job applies the Postgres migrations and runs the full test suite against PostgreSQL 16 (Docker only in CI, never on dev machines).

**5. §5 Upload flow** — `POST /jobs` returns a presigned R2 PUT URL in prod; in local dev the StorageService returns a local upload route on the API itself (e.g. `PUT /jobs/:id/file`). The client just uses whatever URL the API returns, so client logic is identical. File-deletion rule (critical rule #1) goes through the same adapter (R2 delete in prod, disk delete in dev).

**6. §10 Phase 1** — replace "docker-compose (Postgres + MinIO)" with "SQLite via `prisma db push` + local-disk storage adapter". Acceptance criteria: "file deleted from MinIO" → "file deleted from `.local/uploads`". List local prerequisites explicitly: Node 20+, pnpm, Python 3.11, poppler (`pdftoppm`) — no Docker.

**7. §11 Environment variables** — annotate dev vs prod: dev uses `DATABASE_URL="file:./.local/dev.db"`, `STORAGE_DRIVER=local`, `LOCAL_STORAGE_DIR=.local/uploads`; prod uses `DATABASE_URL=postgres://…`, `STORAGE_DRIVER=r2`, plus the `S3_*` keys (marked prod-only).

**8. Phase 4 (DOCX→PDF)** — LibreOffice headless worker container remains a *prod deployment option*; local dev calls a natively installed `soffice` binary on PATH.

**9. New short section "Local development (no Docker)"** — consolidates the story: one `pnpm dev` command starts web + admin + api against SQLite and disk storage; `.local/` is gitignored and swept by the same 60-min deletion cron; the Python simulator agent is unchanged.
